A Team of One

Anthropic has published its own playbook for how a team should run software development with AI doing much of the work. This process follows that same shape, but reshapes it entirely around one person working alone with an AI assistant instead of a team. The checks a team gets from people in a room, a solo developer gets from a second AI model and a fresh conversation instead, and the whole thing runs itself once it's set up.

Here's the actual decision tree, six forks in total. Two of them end the work with no code written at all, a trivial fix handled on the spot, or a plan set aside rather than built right now. An independent reader looks at the work twice, once at the design review and once at the check, and everything else is either a person deciding something or work simply moving forward.

Five ideas, in order

Each builds on the one before it, and none of them require knowing any particular tool.

01

The same playbook, run by one person instead of a team

Anthropic has described how a team should run software development with AI doing much of the work: plan it, build it, review it, ship it. That's the same six-phase shape this process uses. What's missing from any team-shaped version is the one piece that only matters when the collaborator is a context window instead of a colleague. The assistant forgets everything once a conversation ends. Picking work back up, handing it to a fresh conversation partway through, and knowing when to actually stop for the day all become their own discipline, the same reason a handoff document exists between two people on a real team.

02

Checking your own work is weaker than a second, independent read

An AI assistant reviewing its own output uses the same reasoning that produced it in the first place, so it lands on the same answer. That's true for people too. A developer's own code review only counts for something when someone else actually reads it, and this process builds that same independent second look in on purpose. In a fresh conversation with no memory of how the work was produced, a second AI model stands in for the second engineer when there's no person around to do it.

03

How much process a change gets should match how much a mistake would cost

A one-line fix gets fixed and the day moves on. Something with more at stake, a new feature or anything expensive to get wrong, gets a short written plan first, agreed before the work starts. The size and the risk of the change decide the size of the process around it. A fixed process applied to everything either slows down the small stuff or lets the risky stuff through too fast.

04

Four checks happen automatically, at the moments that matter

A tier check decides how much process a piece of work actually earns, and before anything gets built, an independent reader looks over the plan at the design review. The execution check, in turn, confirms the work is being handled with the right amount of care. And once the work is done, a QA check has an independent reader confirm the result against what was actually agreed. Nobody has to remember to ask for any of this. It just fires.

05

"Verified" means checked against something real

A test that ran, a log that got read, a number that got measured: that's what "checked" means here. The single most common failure this catches is work reported as done on the strength of a confident explanation alone.

Workplaces can borrow this too: a team that already has code review and QA can still take pieces of it. Tiering decided by a fixed rule instead of a fresh judgment call each time, checks that fire on their own instead of depending on someone remembering to ask, and a real discipline for picking work back up that doesn't live in one person's memory. What a solo developer had to build from scratch, a workplace can just adopt.
